## 原则零：功能对齐检查 — 所有改动必须符合产品定位

### 0.1 核心理念

> **任何代码修改、功能设计、架构调整，必须首先通过产品定位一致性检查。发现偏离时必须取得用户确认才能继续推进。**

### 0.2 产品核心定位（不可偏离）

| 维度 | 定义 |
|------|------|
| **产品名称** | 桌面宠物 - 灵感助手 |
| **产品定位** | 灵感快速记录与完善的桌面宠物应用 |
| **核心哲学** | 灵感调酒师 → 写作教练单向同步，桌宠作为入口 |
| **核心功能** | A（灵感快速记录）、B（灵感完善）、C（与写作教练同步） |
| **技术栈** | Electron + React + TypeScript + Tailwind CSS |

### 0.3 明确禁止的方向（除非用户明确批准）

| 禁止方向 | 冲突原则 |
|---------|---------|
| 反向同步（写作教练→桌宠） | 单向同步设计 |
| 复杂AI生成功能 | 桌宠定位为记录工具 |
| 移除桌宠形象 | 墨滴桌宠是核心入口 |
| 破坏透明窗口特性 | 桌宠需始终可见 |

### 0.4 功能对齐检查清单

```
□ 这项改动是否符合"灵感记录+同步"的定位？
□ 这项改动是否影响桌宠的透明窗口显示？
□ 新增依赖是否必要？
□ 是否只影响桌宠端，不反向修改写作教练端？
```

## 原则一：设计方案 + Ponytail 精简

### 1.1 核心理念

> **设计先行，代码后行。Ponytail 哲学：最好的代码是你没写的代码。**

### 1.2 Ponytail 精简检查清单

```
□ 这个功能能否用更少的代码实现？
□ 是否引入了不必要的抽象层？
□ 能否复用现有代码而非新建？
□ 新增的依赖是否真的必要？
□ 是否过度设计了（为未来写代码）？
□ 能否用一个函数替代一个类？
```

### 1.3 设计方案必须包含

```
设计方案模板：
□ 功能概述（一句话说清楚做什么）
□ 涉及文件清单（新增/修改哪些文件）
□ 接口/类型定义（IPC channel、Props、Store interface）
□ 数据流图（数据从哪来、到哪去、怎么变）
□ 组件树（UI 层级结构）
□ 边界情况（空状态、错误状态、加载状态）
□ 影响范围（是否影响现有功能）
```

### 1.4 设计阶段禁止事项

- ❌ 跳过设计方案直接写代码
- ❌ 设计方案中没有组件树就开始编码
- ❌ 不评审就进入编码
- ❌ 编码时随意偏离设计方案

## 原则二：写 → 审 → 改 → 查 闭环

### 2.1 核心理念

> **编写和检查必须分离。审查者只给意见不直接修改。**

### 2.2 四轮闭环流程

```
编写者实现 → 审查者检查 → 修复 → 复查 → 通过
                ↓
         ⚠️ 只给意见，不动代码
```

### 2.3 审查铁律

> ⚠️ **审查者永远只输出审查意见，绝不直接修改代码。**

| 审查者可以 | 审查者不可以 |
|-----------|-------------|
| ✅ 指出具体问题位置（文件+行号） | ❌ 直接修改任何代码文件 |
| ✅ 说明问题原因和影响 | ❌ 运行 replace_in_file / write_to_file |
| ✅ 给出修复建议 | ❌ 以"帮你改好了"的方式操作 |
| ✅ 标注严重程度 | ❌ 使用模糊表述（"可能有问题"） |

### 2.4 审查检查清单

```
□ 类型定义是否完整（无隐式 any）
□ Props 接口是否完整
□ IPC channel 命名是否符合规范
□ useEffect cleanup 是否正确
□ 定时器/监听器是否正确销毁
□ 错误处理是否覆盖所有分支
□ 日志记录是否规范
□ 是否引入不必要的依赖
□ 是否影响现有功能
□ 代码风格是否符合项目规范
```

### 2.5 循环上限

最多 3 轮修复-复查。超过则上报主 Agent 介入。

## 原则三：错误库建立

### 3.1 核心理念

> **同样的错误不犯第二次。**

### 3.2 错误记录模板

```markdown
### [E-XXX] 错误标题

| 字段 | 内容 |
|------|------|
| **错误ID** | E-001 |
| **发现日期** | 2026-06-16 |
| **严重程度** | 严重 / 中等 / 轻微 |
| **涉及文件** | `path/to/file.ts` |
| **错误类型** | 类型错误 / 运行时错误 / 逻辑错误 / 规范违反 |
| **错误描述** | 一句话描述错误现象 |
| **错误原因** | 根因分析 |
| **修复方案** | 具体修复步骤 |
| **预防措施** | 如何避免再次发生 |
```

### 3.3 错误库文件位置

`docs/ERROR_LIBRARY.md`

## 原则四：可复用代码库

### 4.1 核心理念

> **不要重复造轮子。写好一次，到处使用。**

### 4.2 目录结构

```
src/
├── shared/
│   └── utils/                    # 共享工具函数
│       ├── debounce.ts
│       └── generate-id.ts
│
├── renderer/
│   ├── components/               # React 组件
│   │   ├── FloatingWidget.tsx    # 桌宠主组件
│   │   └── ui/                  # 通用 UI 组件
│   └── hooks/                   # 自定义 Hooks
│
└── main/
    ├── services/                # 主进程服务
    │   ├── database.ts
    │   └── discovery.ts
    └── tray.ts                  # 系统托盘
```

### 4.3 可复用代码质量标准

- 完整的 TypeScript 类型定义
- 中文 JSDoc 注释
- 无外部副作用
- 单一职责
- 边界情况处理

## 快速检查清单

### 任务开始前
```
□ 是否通过了功能对齐检查？（原则零）
□ 若有偏离产品定位，是否已取得用户确认？
□ 是否有设计方案？（原则一）
□ 设计方案是否经过评审？
□ 是否查阅了错误库中的相关记录？（原则三）
□ 是否有可复用的现有代码？（原则四）
```

### 任务完成后
```
□ 是否更新了错误库（如有新错误）？（原则三）
□ 是否有新的可复用代码需要沉淀？（原则四）
□ Reviewer 的检查清单是否需要更新？
```
