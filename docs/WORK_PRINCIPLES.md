## Karpathy 四原则（LLM 编码行为规范）

> **来源**: [andrej-karpathy-skills](https://github.com/multica-ai/andrej-karpathy-skills)

### K1: 编码前思考 (Think Before Coding)

**不要假设。不要隐藏困惑。呈现权衡。**

- **明确说明假设** — 如果不确定，询问而不是猜测
- **呈现多种解释** — 当存在歧义时，不要默默选择
- **适时提出异议** — 如果存在更简单的方法，说出来
- **困惑时停下来** — 指出不清楚的地方并要求澄清

### K2: 简洁优先 (Simplicity First)

**用最少的代码解决问题。不要过度推测。**

- 不要添加要求之外的功能
- 不要为一次性代码创建抽象
- 不要添加未要求的"灵活性"或"可配置性"
- 如果 200 行代码可以写成 50 行，重写它

### K3: 精准修改 (Surgical Changes)

**只碰必须碰的。只清理自己造成的混乱。**

- 不要"改进"相邻的代码、注释或格式
- 不要重构没坏的东西
- 匹配现有风格，即使你更倾向于不同的写法
- 每一行修改都应该能直接追溯到用户的请求

### K4: 目标驱动执行 (Goal-Driven Execution)

**定义成功标准。循环验证直到达成。**

## 原则零：功能对齐检查

### 0.1 产品核心定位

| 维度 | 定义 |
|------|------|
| **产品名称** | 桌面宠物 - 灵感助手 |
| **产品定位** | 轻量级灵感记录桌面应用 |
| **核心哲学** | AI 辅助人工创作，用户主导全程 |
| **数据流向** | 桌宠 → 灵感调酒师 → 写作教练（单向） |

### 0.2 禁止方向

| 禁止方向 | 原因 |
|---------|------|
| 修改核心同步架构 | 数据必须单向流动 |
| 破坏与灵感调酒师的兼容性 | 需保持 API 接口一致 |
| 全自动流水线 | 违背"用户主导全程" |

### 0.3 检查清单

```
□ 这项改动是否符合"灵感快速记录和完善"的定位？
□ 是否会破坏单向数据同步架构？
□ 是否会影响与灵感调酒师的 API 兼容性？
```

## 原则一：设计方案 + 简洁编码

### 1.1 核心理念

> **设计先行，代码后行。用最少的代码解决问题。**

### 1.2 设计方案必须包含

```
□ 功能概述（一句话说清楚做什么）
□ 涉及文件清单（新增/修改哪些文件）
□ 接口/类型定义（IPC channel、Props、Store interface）
□ 数据流图（数据从哪来、到哪去、怎么变）
□ 组件树（UI 层级结构）
□ 边界情况（空状态、错误状态、加载状态）
```

## 原则二：Subagent 编写 + Subagent 检查

### 2.1 核心理念

> **同一个 AI 不能既当运动员又当裁判。编写和检查必须由不同的 subagent 完成。**

### 2.2 四轮闭环流程

```
用户需求 → Coder 编写 → Reviewer 审查 → Coder 修复 → Reviewer 复查
              ↓            ↓
           通过 ✓      不通过 → 循环（≤3次）
```

### 2.3 Reviewer 禁止事项

| Reviewer 可以 | Reviewer 不可以 |
|--------------|----------------|
| ✅ 指出问题位置（文件+行号） | ❌ 直接修改代码 |
| ✅ 说明原因和影响 | ❌ 使用 replace_in_file / write_to_file |
| ✅ 给出修复建议 | ❌ 以"帮你改好了"方式操作 |
| ✅ 标注严重程度 | ❌ 模糊表述 |

### 2.4 审查检查清单

```
□ 类型定义是否完整（无隐式 any）
□ Props 接口是否完整
□ IPC channel 命名是否符合规范
□ useEffect cleanup 是否正确
□ 错误处理是否覆盖所有分支
□ 日志记录是否规范
□ 是否引入不必要的依赖
□ 是否影响现有功能
□ 代码风格是否符合项目规范
```

### 2.5 审查报告格式

```markdown
# 审查报告 - [任务名称]

## 总体评价
[通过 / 需要修复]

## 问题列表

### [严重] 问题1：xxx
- **位置**: `path/file.ts:行号`
- **问题**: 具体描述
- **影响**: 可能导致的后果
- **建议**: 修复方案

### [中等] 问题2：xxx
- ...

### [轻微] 问题3：xxx
- ...
```

## 原则三：错误库建立

### 3.1 错误库文件

`docs/ERROR_LIBRARY.md`

### 3.2 错误记录模板

```markdown
### [E-XXX] 错误标题

| 字段 | 内容 |
|------|------|
| **错误ID** | E-001 |
| **发现日期** | 2026-06-17 |
| **严重程度** | 严重 / 中等 / 轻微 |
| **涉及文件** | `path/to/file.ts` |
| **错误类型** | 类型错误 / 运行时错误 / 逻辑错误 / 规范违反 |
| **错误描述** | 一句话描述错误现象 |
| **错误原因** | 根因分析 |
| **修复方案** | 具体修复步骤 |
| **预防措施** | 如何避免再次发生 |
```

### 3.3 错误库使用流程

```
发现错误 → 记录到错误库 → 分析根因 → 修复代码 → 更新预防措施
                                              ↓
                                        审查 Checklist 更新
```

## 原则四：可复用代码库

### 4.1 核心理念

> **不要重复造轮子。写好一次，到处使用。**

### 4.2 什么应该进入可复用代码库

| 类别 | 条件 | 示例 |
|------|------|------|
| **工具函数** | 被 3+ 处调用 | `debounce()`, `generateId()` |
| **自定义 Hooks** | 跨组件复用 | `useChat`, `useLocalModel` |
| **UI 组件** | 通用 UI 元素 | `Toast`, `Dialog` |

### 4.3 可复用代码质量标准

- [ ] 完整的 TypeScript 类型定义
- [ ] 中文 JSDoc 注释
- [ ] 无外部副作用
- [ ] 单一职责
- [ ] 边界情况处理

## 快速检查清单

### 开始任务前

```
□ 是否通过了功能对齐检查？（原则零）
□ 是否有设计方案？（原则一）
□ 是否计划使用 Coder + Reviewer 双 subagent？（原则二）
□ 是否查阅了 ERROR_LIBRARY.md 避免重复踩坑？（原则三）
□ 是否有可复用的现有代码？（原则四）
```

### 任务完成后

```
□ typecheck 通过？（npm run typecheck）
□ oxlint 通过？（npm run lint）
□ prettier 格式化？（npm run format）
□ 是否更新了错误库（如有新错误）？（原则三）
□ 是否有新的可复用代码需要沉淀？（原则四）
```
